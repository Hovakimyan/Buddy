# End-to-end checklist

What to check on a real Mac and a real iPhone, and what the automated tests already prove, so you only spend time on
what software cannot see.

**How to read it**

- **Automated** rows name the test that backs them. `swift test` (BuddyKit), `xcodebuild -scheme BuddyMac ... test` and
  `xcodebuild -scheme BuddyPhone ... test` run them; none touches your real `~/.claude`, `~/Library/Application
  Support/Buddy`, iCloud or CloudKit. The failure drills F1 to F11 run the real `buddy-hook` binary against a real
  `BuddyEngine` on a temporary socket (`Tests/BuddyKitTests/EndToEndDrillTests.swift`).
- **Real device only** rows need the signed Mac app, a signed iPhone build and the same Apple Account on both
  (`docs/cloudkit-setup.md`). The tests cannot cover them: no real iCloud, push, Face ID, notch hardware, speakers or
  Claude Code.
- **Result (Mac / iPhone)** is blank on purpose. Write `pass`, `fail` or `n/a` and a date. For a `fail`, fix it and add a
  regression test before ticking it.

**Setup.** Signed `BuddyMac` running (menu bar icon, menu says `Phone link on`), hooks installed from Settings (see
README), signed `BuddyPhone` installed, notifications allowed, both signed in to the same iCloud account. Two terminals in
two different project folders running `claude`. To make Claude Code ask for permission, ask it to run a command that is
not already allowed (for example `touch /tmp/buddy-check`).

## 2. Failure drills

For each drill, "silent" means the hook prints nothing and exits 0, so Claude Code asks in the terminal as it would
without Buddy. Allow a few seconds for the terminal prompt to appear where a row says so.

| ID | Steps | Expected | Automated by | Result (Mac / iPhone) |
| --- | --- | --- | --- | --- |
| F1 | Trigger a permission request, leave it pending, then **Quit Buddy** from the menu. | The terminal prompt appears at once (no 110 s wait). Restarting Buddy shows no stale card. | `EndToEndDrillTests.engineStoppedMidApprovalLeavesHookSilent`. **Real only:** the quit path of the app. | |
| F2 | Put the iPhone in airplane mode, trigger a request, answer on the Mac card. Then turn airplane mode off. | The Mac card works as normal and answers Claude Code. After it reconnects, the phone no longer offers the request: it is updated when the Mac's update gets through, and hidden at the request's expiry time at the latest. A phone decision for a request already answered on the Mac is ignored. | The Mac path does not depend on the phone: `BuddyEngineTests.engineWorksWithNilTransport`, `PhoneBridgeTests.transportFailureDoesNotBlockQueue`, `failedPublishRetriesWithBackoff`. First decision wins: `EndToEndDrillTests.phoneDenyWinsOverLaterMacAllow` (F2/F3). **Real only:** the radio and the reconnect. | |
| F3 | Break the Mac's CloudKit access (sign out of iCloud and restart Buddy, or disconnect the network), trigger a request, answer on the Mac card. | The menu says `Phone link off: <reason>` (or publishes are retried and dropped), the Mac card and Claude Code answer work as normal. | `PhoneLinkTests`, `PhoneBridgeTests.publishIsDroppedAfterAllRetriesAndLeavesNothingRunning`, `publishStormWithFailingTransportStaysBoundedAndQueueStillResolves`. **Real only:** real CloudKit errors. | |
| F4 | Trigger a request, then answer it in the terminal instead of the card. | The card clears on the Mac and the phone. | F5 | Run two sessions at once and trigger a request in each before answering either. | F6 | Trigger a request and do nothing for about 105 s, then try to click Allow (Mac) or Allow (iPhone). | The request expires after 105 s and the hook goes silent (terminal prompt). A late click or late phone decision is refused and allows nothing. | `EndToEndDrillTests.decisionAfterTimerExpiryIsRejectedAndHookIsSilent`, `decisionPastExpiryBeforeTimerFiresIsRejectedAndHookIsSilent`, `BuddyEngineTests.defaultApprovalTimeoutEndsBeforeTheRelayStopsWaiting`, `PhoneBridgeTests.decisionAfterExpiryIsIgnored`. | |

Do it only in a safe local run: a temp copy, with BOTH `BUDDY_SETTINGS` and `BUDDY_HOME` pointing into a temp directory (`Apps/README.md`, "Safe local runs"). (b) Same, and the running Buddy shows no new session and keeps working. | `EndToEndDrillTests.garbageAndOversizedStdinNeverPrintOrFailAndDoNotDisturbTheApp`, `BuddyHookProcessTests`. | |

## 3. Manual checks: Mac app

Not covered by tests because they need a display, speakers or the notch.

| ID | Steps | Expected | Result (Mac / iPhone) |
| --- | --- | --- | --- |
| M1 | Launch BuddyMac with no sessions. | No dock icon. Menu bar icon with the menu; no island panel while everything is idle. | |
| M2 | Start a session and run a long tool. | The island peeks (the peek sound plays): Block beside the notch with "Working". Block is amber, eyes darting, with a three-dot badge. It hides again about a minute after the last event. | |
| M3 | Trigger a permission request. | The island opens with the card at the notch (or a centred bar at the top on a Mac without a notch) and the approval sound plays. It does not take keyboard focus. Block is orange with wide eyes and a "!" badge: it hops, then bounces gently while waiting. | |
| M4 | With an app other than a terminal in front (the finish and error sounds are skipped while a terminal is frontmost), let a session finish, then make one fail. | Finish: the finish sound, and Block turns green with happy arc eyes, spins and sparkles, for about 5 s. Error: the error sound, and Block turns red with flat eyes after a quick shake. Every sound is a short CC0 cue from `Apps/BuddyMac/Resources/sounds/block/` (listed in its `SOURCES.md`), all about as loud as each other and none harsh. Peeking, opening and closing the island and hovering over Block play their own short cues; the mute button in the island header (or ⌃⌥M) silences every cue. | |
| M4c | Turn on System Settings > Accessibility > Display > Reduce motion, then repeat M2 and M3. Hover the hidden island to peek. | Block no longer moves: no hop, bounce, spin, shake or darting eyes, and the badges hold still (a still "z" while asleep), but every state is still told apart by its colour, eyes and badge. The island changes size at once and its content fades instead of springing open. Peeking on hover shows Block idle (blue, round eyes). At the notch each state is legible at a glance. | |
| M4b | Let a session finish and leave it alone for a few minutes (Claude Code then sends its "waiting for your input" reminder). | The session stays idle: the island does not open or peek and the session does not show as waiting. | |
| M5 | Use a request with unusual text: a command with invisible or look-alike characters, a command of about 180 characters, one with many emoji. | Hidden characters show as `‹U+XXXX›`. | M7 | Settings > **Uninstall hooks…** and Confirm. | Only Buddy's entries are removed (backup kept), status reads "Hooks not installed". | |
| M8 | Start the app while another copy holds the socket, or with the socket path unusable. | The menu shows `Not listening: <reason>`. It does not show "Not listening" while it is still starting up. | |

## 4. Manual checks: CloudKit and iPhone

These need the signed builds from `docs/cloudkit-setup.md`. Use that document's section 8 for the phone-specific steps
and troubleshooting.

| ID | Steps | Expected | Result (Mac / iPhone) |
| --- | --- | --- | --- |
| C1 | Launch the signed Mac app. | Menu says `Phone link on`. | |
| C2 | CloudKit Dashboard > Data > private database > zone `Buddy`: open an `Approval` and a `Session` record. | `tool`, `summary`, `project` and `lastTool` show as encrypted (not readable). | |
| C3 | Launch BuddyPhone, allow notifications. | Session list shows the running sessions after a pull to refresh. | |
| C4 | Start the phone with no iCloud (airplane mode at launch, or iCloud signed out), then fix it and bring the app back to the foreground. | A timeout or temporary unavailability is checked again on foreground and connects. "Not signed in" or "restricted" stays until relaunch. The status line says which. | |
| C5 | Lock the phone, trigger a request, tap **Deny** in the notification while a network drop makes it fail (for example airplane mode just before the tap). | A notification "Could not deny — answer on your Mac" appears. The request is still answerable on the Mac. | |
| C6 | Open an approval on the phone, then change the request on the Mac side while the Face ID prompt is up (answer it in the terminal). | Nothing is allowed on the Mac. If the update reached the phone before Face ID returned, nothing is sent and the screen says it was already answered. Otherwise the phone may still send its Allow, and the Mac ignores it because the request is no longer pending. | |
| C7 | Open an approval screen, go back, open another approval. | Each screen starts fresh: Allow arms again for the new request. | |
| C8 | Use a request with hidden characters or a long command on the iPhone. Then one with Hebrew or Arabic text (for example `echo שלום && ls`). | Whole command is readable (scrolls); hidden characters show as `‹U+XXXX›`; a truncated command offers only Deny. The Hebrew or Arabic command offers only Deny and "Allow on your Mac", like the Mac card. | |

## 5. Run the automated checks

```sh
swift test
cd Apps && xcodegen generate
xcodebuild -scheme BuddyMac -destination 'platform=macOS' test
xcodebuild -scheme BuddyPhone -destination 'platform=iOS Simulator,name=<a simulator you have>' test
```

Expected: every test passes and the builds report no warnings (warnings are errors in the Xcode projects).
